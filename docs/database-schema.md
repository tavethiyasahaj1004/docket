# Database Schema

## Overview

PostgreSQL database accessed via Drizzle ORM. All schemas are in `db/schema/`. Migrations are in `db/migrations/`.

All IDs are **cuid2** strings (from `@paralleldrive/cuid2`), except `ticket_number` which is a PostgreSQL serial integer.

### `mcp_access_tokens`

├── revoked_at        timestamp with time zone, nullable   ← soft revoke; the row is kept for history

```

#### Automatic revocation trigger

Migration `0017` installs `mcp_access_tokens_revoke_on_user_update`, an `AFTER UPDATE ... FOR EACH ROW`
trigger on `"user"` (function `mcp_revoke_tokens_for_ineligible_user()`). It fires whenever an update
leaves the row **banned** (`banned IS TRUE`) or with a `role` other than exactly `agent` or `admin`,
and revokes every still-live token of that user: `revoked_reason` is `user_banned` when the user is
banned, otherwise `role_changed`.

- **State-based, not transition-based.** It looks at the row after the update, not at what changed,
  so it covers every path that can write `"user"`: Docket's own routes and actions, Better Auth's admin
  endpoints, and direct SQL.
- **Revocation is permanent.** Nothing clears `revoked_at`. Unbanning, a timed ban expiring or
  restoring the role does not bring a token back; the owner creates a new one.
- **Original history is preserved.** It only touches rows with `revoked_at IS NULL`, so a token that was
  already revoked keeps its original `revoked_at` and `revoked_reason`.
- **No actor audit event.** A trigger cannot know who acted; the token row's
  `revoked_at`/`revoked_reason` is the record. The two Docket ban paths (`PATCH /api/users/[id]` and the
  Orbit ban action) revoke the tokens themselves, inside the ban's transaction, and write one
  `mcp_token.revoked` audit row per token with the acting admin — so the trigger finds nothing left to do
  there. Signing out other sessions likewise revokes tokens (`sessions_signed_out`) and audits each.
- **Permissions.** The trigger writes `mcp_access_tokens` as the role that updates `"user"`, so any
  database role that updates `"user"` also needs `UPDATE` on `mcp_access_tokens`.
- **Serialization with token creation.** Creating a token locks the owner's `user` row `FOR SHARE`
  (the plain foreign-key check would not conflict with a concurrent ban), and the Docket ban paths lock it
  `FOR UPDATE`, so a ban and a token insert can never interleave and leave a live token behind.
- **On-use backstop.** Inserts do not fire the trigger, so verifying a token whose owner is not eligible
  (or has `banned` set, even if `ban_expires` has passed) revokes it with `account_not_permitted`.

### `mcp_tool_calls`

Operational trace of MCP tool calls, doubling as the idempotency and per-ticket lock ledger for write
tools. Rows hold **no message bodies or tool arguments** — only keyed HMACs of them — and are intended to
be pruned after 30 days.

```
mcp_tool_calls
├── id                  text PK (cuid2)
├── request_id          text NOT NULL
├── user_id             text, nullable → user.id (SET NULL on delete)   ← the trace survives account erasure; no name/email is snapshotted here
├── auth_method         text NOT NULL
├── credential_id       text, nullable            ← no foreign key on purpose: may later reference something other than an access token (e.g. an OAuth grant)
├── tool                text NOT NULL
├── client_request_id   text, nullable            ← caller-supplied idempotency key
├── status              mcp_tool_call_status NOT NULL   ← pending | succeeded | failed
├── error_code          text, nullable
├── args_hmac           text, nullable            ← keyed HMAC of the arguments, never the arguments
├── planned_entity_id   text, nullable
├── lock_group          text, nullable
├── target_ticket_id    text, nullable            ← no foreign key; the ticket a call resolved to (read tools, and write tools on their ledger row, with or without a lock_group)
├── target_customer_id  text, nullable            ← no foreign key; `get_customer` records the customer it resolved to
├── body_hmac           text, nullable            ← keyed HMAC of a message body, never the body
├── lease_expires_at    timestamp with time zone, nullable
├── attempts            integer NOT NULL DEFAULT 1
├── result_json         jsonb, nullable
├── side_effects_uncertain boolean NOT NULL DEFAULT false
├── notification_errors text[], nullable          ← null = none
├── duration_ms         integer, nullable
├── created_at          timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at          timestamp with time zone NOT NULL DEFAULT NOW()

UNIQUE INDEX mcp_tool_calls_idempotency_idx ON (user_id, tool, client_request_id) WHERE client_request_id IS NOT NULL
UNIQUE INDEX mcp_tool_calls_ticket_lock_idx ON (lock_group, target_ticket_id) WHERE status = 'pending' AND lock_group IS NOT NULL
INDEX mcp_tool_calls_created_at_idx ON (created_at)
INDEX mcp_tool_calls_user_idx ON (user_id)
```

`mcp_tool_call_status` is a PostgreSQL enum (`pending`, `succeeded`, `failed`).

A write call that crashed leaves its row `pending`, and while it is pending it holds the per-ticket lock
(`mcp_tool_calls_ticket_lock_idx`), so a call with a different `clientRequestId` on that ticket gets
`in_progress`. The worker job `mcp.pending-calls-sweep` runs every 5 minutes and settles each `pending` row
whose `lease_expires_at` passed more than 5 minutes ago (a row with no lease is aged by `updated_at`
instead): it runs the tool's reconcile check, marking the row `succeeded` with `side_effects_uncertain` if the
write turns out to have happened, or `failed` with `error_code = 'interrupted'` otherwise. That releases the
lock, so a crashed holder blocks its ticket for at most about 6 to 11 minutes. The daily `mcp.tool-calls-prune`
job does the same for any `pending` row created over an hour ago, then deletes rows older than 30 days.

Every MCP call leaves exactly one row. A write call that claims the ledger is recorded on its ledger row
(`client_request_id` when given, `planned_entity_id`, `target_ticket_id`, `result_json` of ids only). Every
other call (reads, input or ticket-resolution failures, replays, `in_progress`, `idempotency_key_reused`)
gets one trace row with no key.

### `mcp_pending_actions`

A close or a reply an MCP client asked for, waiting for the token owner to approve or dismiss it in Docket
(see [mcp.md § Approval requests](./mcp.md#approval-requests-closing-and-replying)). Customers never see this
table: the customer portal and the v1 API do not read it.

```
mcp_pending_actions
├── id                      text PK (cuid2)
├── kind                    mcp_pending_action_kind NOT NULL     ← close | reply
├── ticket_id               text NOT NULL → tickets.id (CASCADE on delete)
├── requested_by_id         text NOT NULL → user.id (CASCADE on delete)   ← the token owner, and the only person who may decide
├── credential_id           text, nullable → mcp_access_tokens.id (SET NULL on delete)
├── tool_call_id            text, nullable      ← the mcp_tool_calls row that created it; no foreign key, because ledger rows are pruned
├── payload                 jsonb NOT NULL DEFAULT '{}'   ← {} for a close; { content } (Tiptap JSON, as stored on the comment) for a reply
├── status                  mcp_pending_action_status NOT NULL DEFAULT 'pending'   ← pending | approved | dismissed | expired | cancelled | failed
├── status_reason           text, nullable      ← why it was cancelled or failed: token_revoked | ticket_merged | replies_disabled | ticket_closed | ticket_not_found | no_closed_status | interrupted
├── planned_entity_id       text, nullable      ← the activity or comment id an approval will create; set by the approving compare-and-set
├── result                  jsonb, nullable     ← ids and booleans only: { activityId } | { commentId } | { alreadyClosed: true }, optionally notificationErrors
├── side_effects_uncertain  boolean NOT NULL DEFAULT false
├── decided_at              timestamp with time zone, nullable   ← approved or dismissed
├── expires_at              timestamp with time zone NOT NULL     ← created + 24 hours
├── created_at              timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at              timestamp with time zone NOT NULL DEFAULT NOW()

UNIQUE INDEX mcp_pending_actions_pending_idx ON (ticket_id, kind, requested_by_id) WHERE status = 'pending'
INDEX mcp_pending_actions_credential_idx ON (credential_id)
INDEX mcp_pending_actions_status_idx ON (status)
INDEX mcp_pending_actions_requested_by_idx ON (requested_by_id)
```

`mcp_pending_action_kind` and `mcp_pending_action_status` are PostgreSQL enums.

- **One pending request** per ticket, kind and person (the partial unique index).
- **Actionable** means `status = 'pending'`, not past `expires_at`, with a credential that is not revoked and still belongs to the requester, and a requester who is still an unbanned agent or admin. Token *expiry* does not matter, only revocation. Every read and the approve/dismiss compare-and-set use this one definition, so an expired or orphaned row is never actionable even before it is marked.
- **Approving** is one conditional `UPDATE ... WHERE id = $id AND requested_by_id = $user AND <actionable> RETURNING`, which sets `status = 'approved'`, `planned_entity_id` and `decided_at`; only one concurrent approval can win. The service then runs, and writes `result` (or `status = 'failed'`) with an `UPDATE ... WHERE status = 'approved' AND result IS NULL`.
- **Crash recovery.** The worker job `mcp.pending-calls-sweep` (every 5 minutes) settles `approved` rows with no `result` whose `decided_at` is more than 5 minutes old, from the database alone: it looks for the comment or `ticket_closed` activity row with `planned_entity_id`, records `result` (with `side_effects_uncertain`) if it exists, and otherwise sets `failed` / `interrupted`. It never runs the action or sends anything.
- **Expiry.** The daily `mcp.tool-calls-prune` job marks pending rows past `expires_at` as `expired`.

#### Cancellation trigger

Migration `0018` installs `mcp_pending_actions_cancel_on_token_revoke`, an `AFTER UPDATE OF revoked_at ... FOR EACH ROW` trigger
on `mcp_access_tokens` (function `mcp_cancel_pending_actions_on_token_revoke()`), firing when `revoked_at` goes from NULL to a value.
It sets that token's pending rows to `cancelled` with `status_reason = 'token_revoked'`.

- It covers every revoke path: Docket's own, the `"user"` trigger from `0017` (ban or role change), the verify-time backstop and direct SQL.
- Trigger-driven cancellations write no audit row (like the token revocations themselves). Docket's own revoke paths (token revoke by the owner or an admin, the two ban paths, signing out other sessions) cancel and write `mcp.action_cancelled` first, with the acting user, so the trigger finds nothing left to do for them.
- A ticket merge cancels the pending rows of the merged-away tickets (`status_reason = 'ticket_merged'`, audited with the merging user); the surviving ticket's rows are untouched.

├── id                text PK (cuid2)
├── key               text NOT NULL UNIQUE   ← stable machine key, auto-slugified from label; used in API payloads
├── label             text NOT NULL
├── type              text NOT NULL          ← "text" | "number" | "date" | "checkbox" | "select"
├── options           jsonb                  ← string[], only set when type = "select"
├── required           boolean NOT NULL DEFAULT false
├── sort_order        integer NOT NULL DEFAULT 0
├── created_at        timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at        timestamp with time zone NOT NULL DEFAULT NOW()
```

### `ticket_custom_field_values`

Per-ticket values, one row per (ticket, field). Deleting a field definition cascades here (unlike categories/statuses, this is a real FK, not a denormalized slug string, so there's no "blocked because in use" check on delete).

```
ticket_custom_field_values
├── id                text PK (cuid2)
├── ticket_id         text NOT NULL → tickets.id (CASCADE DELETE)
├── field_id          text NOT NULL → ticket_custom_fields.id (CASCADE DELETE)
├── value             text            ← always stored as text: "true"/"false", numeric string, ISO date, or the selected option
├── created_at        timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at        timestamp with time zone NOT NULL DEFAULT NOW()

Indexes:
- (ticket_id, field_id) unique
- field_id
```

### `user_ticket_table_prefs`

Per-agent/admin display preferences for the `/tickets` table — which columns are shown and in what order. One row per user, not shared.

```
user_ticket_table_prefs
├── user_id            text PK → user.id (CASCADE DELETE)
├── columns            jsonb NOT NULL   ← ColumnPref[]: [{ id: "status", visible: true }, ...] in display order
└── updated_at         timestamp with time zone NOT NULL DEFAULT NOW()
```

### `ticket_reply_drafts`

An agent's unsent reply on a ticket, auto-saved by the reply composer. One row per (ticket, agent); deleted when the reply is sent, discarded, or emptied.

```
ticket_reply_drafts
├── ticket_id          text NOT NULL → tickets.id (CASCADE DELETE)
├── user_id            text NOT NULL → user.id (CASCADE DELETE)
├── content            text NOT NULL   ← Tiptap JSON, same as ticket_comments.content
├── is_internal        boolean NOT NULL DEFAULT false
├── created_at         timestamp with time zone NOT NULL DEFAULT NOW()
├── updated_at         timestamp with time zone NOT NULL DEFAULT NOW()
└── PRIMARY KEY (ticket_id, user_id)
```

### `ticket_links`

Agent-only relationships between tickets (see `docs/tickets.md` § Merge, Split & Link). One row per link, read from both ends; `related_to` is symmetric, `duplicate_of` and `blocks` are directional.

```
ticket_links
├── id                 text PRIMARY KEY (cuid2)
├── ticket_id          text NOT NULL → tickets.id (CASCADE DELETE)
├── linked_ticket_id   text NOT NULL → tickets.id (CASCADE DELETE)
├── type               text NOT NULL   ← 'related_to' | 'duplicate_of' | 'blocks'
├── created_by_id      text → user.id (SET NULL on delete), nullable
├── created_at         timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at         timestamp with time zone NOT NULL DEFAULT NOW()

Indexes:
- (ticket_id, linked_ticket_id, type) unique
- linked_ticket_id
```

### `push_subscriptions`

Browser Web Push (VAPID) subscriptions for agents — one row per browser profile. Only used when the push provider is `webpush` (Admin → Integrations → Push Notifications); Pusher Beams keeps its own device registry. Rows are pruned when the push service answers 404/410, and all rows are deleted when the VAPID key pair changes (browsers re-subscribe on next load). See `docs/in-app-notifications.md`.

```
push_subscriptions
├── id                 text PRIMARY KEY (cuid2)
├── user_id            text NOT NULL → user.id (CASCADE DELETE)
├── endpoint           text NOT NULL UNIQUE   ← push-service URL; upsert key
├── p256dh             text NOT NULL          ← client public key
├── auth               text NOT NULL          ← client auth secret
├── user_agent         text
├── created_at         timestamp with time zone NOT NULL DEFAULT NOW()
└── updated_at         timestamp with time zone NOT NULL DEFAULT NOW()
```

`platform_settings` gained seven ticket-action switches, all `boolean NOT NULL DEFAULT true`
(Admin → Ticket Config → Ticket Actions): `ticket_merge_enabled`,
`ticket_merge_notifications_enabled`, `ticket_merge_customer_email_enabled`,
`ticket_split_enabled`,
`ticket_split_notifications_enabled`, `ticket_link_enabled`,
`ticket_link_notifications_enabled`.

`platform_settings` also holds the admin-configurable attachment caps (Admin → Ticket Config →
Attachment Limits), all `integer NOT NULL`: `attachment_max_per_message` (default 5),
`attachment_max_file_size_mb` (10) and `attachment_max_per_ticket_size_mb` (250 — combined size of a
ticket's attachments, summed live from `ticket_attachments.file_size`). Out-of-range stored values fall back to the defaults on read
(`resolveAttachmentLimits` in `lib/tickets/attachment-limits.ts`). `attachment_max_per_ticket`
(default 25) still exists but is **deprecated and unused** — Docket does not limit a ticket's attachment
*count*; the column was left in place to avoid a destructive migration.

`platform_settings` also holds `mcp_enabled` (`boolean NOT NULL DEFAULT false`), the admin switch for the
MCP endpoint — off by default — and `mcp_customer_replies_enabled` (`boolean NOT NULL DEFAULT false`, migration
`0019`), the admin gate for customer replies requested over MCP (`reply_to_customer`). While it is false the tool is not
registered and a pending reply request cannot be approved; turning it off cancels the pending reply requests
(`mcp_pending_actions.status_reason = 'replies_disabled'`) in the same transaction.

`integration_settings` also gained `push_provider` (`pusher` | `webpush`, null = env/`pusher`) and the Web Push VAPID columns (`web_push_vapid_public_key`, `web_push_vapid_private_key_encrypted`, plus the usual `web_push_last_test_*` trio).

## Drizzle Conventions

- Use `pgTable` from `drizzle-orm/pg-core`.
- Enums are stored as `text` with a comment or Zod enum for validation — not PostgreSQL `ENUM` type (makes migrations simpler).
- All timestamps use `timestamp({ withTimezone: true })`.
- All IDs use `text().primaryKey()` — no `serial` except for `ticket_number`.
- `updatedAt` is updated manually in every write operation — not via a database trigger.
- Foreign keys use `references(() => table.column, { onDelete: 'cascade' })` or `{ onDelete: 'set null' }` as appropriate.
